# QwenReplyHelper — 本地 Qwen 的 X 回复 Chrome 扩展（v1.2.7，三模型）

## v1.2.7 改动（工具条常驻右下角 + 打开 X 就出现 + 只有拖动才动 + 状态文案去掉 Qwen）

用户确认的要求：工具条不要再乱跑，不要只在点评论图标后才出现，也不要
在关回复框后就消失；要一直在右下角、稍微靠下的地方待着，不拖就不动。

新版（只改 `content.js` + `styles.css` + 版本/文档，模型、端口、提示词、
风格、紫色主题、标题“本地回复”全部不变）：
- **默认位置固定在右下角**：`position: fixed`，右 20px、下 20px，宽 520px、
  不超过屏幕宽的 90%，由 content.js 换算成 left/top 像素值（这样拖动才不会跳位置）。
- **打开 X 就出现**：扩展一加载就在时间线上建好工具条，状态是待命文案
  “点某条帖子的评论图标开始生成”，模型/风格按钮都可见，但此时还没有选帖子。
- **点评论图标时同一个工具条原地生成**：不再每次点气泡就删掉重建、回到顶部中间；
  点气泡只是把同一个工具条从待命切到生成，位置一动不动，生成、切模型、
  切风格、重新生成都不会重新定位它。
- **只有拖动才动**：按住顶部标题行拖动才会移动位置，拖动后位置记在
  `chrome.storage.local` 的 `qrhToolbarPos` 里，下次打开 X 会恢复到上次拖到的位置；
  从来没拖过，就每次都在右下角，不会自己跑。
- **关回复框不再让工具条消失**：关回复框只取消在途生成、回到待命状态，
  工具条仍在原位置待着，等下一次点评论图标；只有 X 页面本身卸载时它才随页面消失。
  换帖子仍会先取消上一通生成（单飞行不变），切模型期间按钮仍全部变灰不可点。
- **待命时点风格/重新生成不会瞎生成**：没有选帖子时点风格只换选中态、
  点重新生成只换状态提示，状态会明确写“还没有选帖子：先点某条帖子的评论图标，
  再选风格/再点重新生成”，不会发没有帖子的生成请求，也不会报错。待命时点模型
  可以先切好模型（切好后提示“已切换到××，点某条帖子的评论图标开始生成”），
  等点了气泡再用新模型生成。
- **拖动时生成中、文字永远填不进来的修复（同属 v1.2.7 代码，必须修）**：
  用户确认：状态显示“生成中”时拖动工具条，生成好的文字就再也进不了回复框。
  原因很可能是工具条在 X 回复框对话框外面，标题行的 mousedown/mouseup
  会被 X 当成对话框外的点击/焦点丢失，填入路径于是对着一个已失焦或
  正在关闭的编辑框跑。修法分三点：(1) 标题行 mousedown（capture 阶段）、
  mousemove、mouseup 都 stopPropagation 并 preventDefault，拖动结束后的
  那次点击也只对工具条目标拦截一次，X 收不到拖动造成的对话框外点击，
  也抢不走编辑框焦点；按钮不在标题行里，点按钮不受影响；(2) 拖动代码
  绝不碰生成状态——不取消、不改 generationSeq、不改 state，只移动卡片；
  (3) 生成在拖动中完成时不丢弃、也不硬填：结果先存进 pendingFill，状态
  写“生成完成，松开鼠标后填入…”，松开鼠标时 onUp 再校验着填一次
  （编辑框已不在就丢弃），状态按校验结果报“已填入”或“填入失败，
  请再点一次重新生成”，不再谎报成功；新一通生成开始时会先丢弃上一通
  未填的 pendingFill，防止旧文字落进新回复框；关回复框也会清掉 pendingFill。
- **换风格后旧文字残留的修复（同属 v1.2.7 代码）**：用户实测换风格后状态
  显示“已填入”，但回复框里仍是第一次生成的新风格文字根本没换上去。原因是
  旧的重新生成路径在工具条点击已经抢走编辑框焦点/选区之后，才用
  `execCommand('selectAll') + execCommand('delete')` 清框，在 X 编辑框里经常
  删不掉，旧代码又不检查填入结果就直接报成功。现在重新生成时先用 DOM
  直接删掉编辑框的全部子节点、把光标放回开头、发一次 input 事件，再走
  原来的填入路径；填完会校验框里确实有新文字的前 10 个字，且重新生成时
  旧文字已不在（旧文字在前、或新文字追加在旧文字后面都算失败），校验通过
  才显示“已填入，可修改后点 Reply”，否则显示“填入失败，请再点一次重新生成”，
  不再谎报成功。单飞行、切模型/换帖取消逻辑不变。
- **状态文案里的 Qwen 也去掉了**：底部状态行的“本地 Qwen 生成中…”改成
  “本地生成中…”，“请先启动电脑本地 Qwen 服务”改成“请先启动电脑本地服务”。
  工具条/状态里不再有 Qwen 字样；模型文件名、端口、别名、代码注释和文档里的
  模型名不在此列（那是文件名/技术名，不是工具条文案），扩展名本身也不改。

## v1.2.3 修复（端口被旧进程占着，管理器不再起第二个进程打架）

用户反馈：黑窗口都关了，再双击 start-manager 还是报
“couldn't bind HTTP server socket, hostname: 127.0.0.1, port: 18080”。
原因不是用户没关干净：关黑窗口不等于旧 llama-server 一定死了，
上一次管理器跑过的孤儿进程、或者同时开的第二个管理器，都可能还
占着 18080，旧管理器却不管不顾又起第二个进程，结果必然绑端口失败。

新版管理器（v1.2.3，`qwen-manager.py`）改成这样：
- 起模型之前先查该端口的 /health。如果已经健康，**直接复用，不再起
  第二个进程**，黑窗口和返回信息里明确写“端口已有一个健康服务在跑，
  直接复用，不再起第二个进程”，并把当前模型记成这个端口对应的模型。
- 被复用的外部进程，管理器**永远不会杀它**：切走它时只清掉当前模型
  标记，外部进程继续在原端口跑；只有管理器自己起的进程，切走时才
  会被杀掉并等端口释放。
- 如果端口是通的但 /health 不通（死进程/外来进程占着端口），管理器
  不会再起一个注定绑失败的进程，而是直接报：“端口 18080 已被旧进程
  占用：请重启电脑，或在任务管理器详细信息里结束 llama-server.exe
  后再双击 start-manager；不要同时开两个管理器黑窗口，也不要同时
  点 start-qwen 单脚本”。
- 第二个管理器实例也会先抢 8090，抢不到就直接打印“已有另一个管理器
  在跑”，退出，不启动、不杀任何模型。
- v1.2.2 的 --reasoning 自动重试、三个模型、四个风格、端口和提示词
  全部不变。日常仍是：**只双击一次 start-manager.bat**。

## v1.2.2 修复（真实 Windows 报错，llama.cpp b12038，不用用户手动改文件）

用户在 Windows 上双击 start-manager.bat 后，管理器报“模型进程提前退出
（exit=1）。可能是该 llama-server 不认 --reasoning off”。这是该版本
llama-server 本身不认 `--reasoning off` 这个参数，不是模型文件坏了，
也不是 DLL 缺了。**用户不需要手动改 qwen-manager.py 或任何脚本。**

管理器现在自动处理：先按原来那样带 `--reasoning off` 起一次；如果进程
提前退出、且日志里提到 reasoning 或 invalid argument，就**自动再起一次，
这次去掉 `--reasoning`，并等 /health 通了才算成功**，黑窗口和返回信息里
都会明确写“已自动去掉 --reasoning off 重试，因为该版本 llama-server 不认这个参数”。
如果第二次也失败，报错里给的是**第二次**的日志尾部，不是第一次的，
不要再按第一次的日志去排查。其他提前退出（缺 DLL、模型文件坏、端口被占）
日志里没有 reasoning 字样时，不会触发这次重试，会直接报真实原因。

去掉该参数后，非思考行为靠什么保证：
- 新模型 Qwen3-4B-Instruct-2507 本身就是非思考设计，去掉参数也是安全的，
  它本来就不会输出思考内容。
- 旧 4B 和混合思考的 8B 去掉参数后可能输出思考内容，但扩展的提示词仍说
  “一两句说完”“不要思考过程”，且 background.js 会把回复里的
  `<think>...</think>` 块去掉（只去这些块，不动其他正文）再填入回复框，
  所以回复框里不会出现思考过程。
- 单模型备用脚本里的 `--reasoning off` 参数本身没有删掉（老版本需要它），
  脚本注释已写清：管理器会自动重试；手动跑单脚本时如果你的版本也报这个错，
  删掉那一个参数再跑一次即可。

**只做一件事，两次点击回复：**

1. 在 Chrome 打开 X 的 For You 时间线或帖子详情页，点击某条帖子的原生评论图标。
   扩展自动读取**被点击的那条主帖正文**，调用**电脑本地**运行的 Qwen 模型生成评论，
   并直接填入 X 原生回复输入框。
2. 用户自己检查、修改，然后点击 X 原生 Reply 按钮，完成发布。

不需要复制帖子，不需要手动粘贴，不需要额外点击生成按钮。
扩展**不会**替用户点 Reply，**不会**自动发送。

## 切换模型：一点就切，跟手机一样（但要先开管理器）

手机上一点就切，是因为 App 自己控制 llama-server 进程，停旧起新都在 App 里。
Chrome 扩展在浏览器沙箱里**不能直接起停电脑上的进程**，所以单靠扩展做不到，
必须加一个电脑本地的小管理器来替它起停。这是如实说明，不是少了个按钮。

- **日常只做一件事：双击一次 `start-manager.bat`（Mac/Linux：`sh start-manager.sh`），
  黑窗口开着就行。** 管理器（`qwen-manager.py`，只用 Python 标准库，无外部依赖）
  会自动先起默认新模型（18080），以后你在 X 回复框工具条里点“新模型 2.5GB” /
  “旧 4B 3.01GB” / “8B 5.03GB”，就是一点就切：管理器先杀旧进程、等端口释放、再起新模型、
  等 /health 通了才返回成功，成功后扩展再用新模型生成一次。
- **模型加载要十几秒到几十秒，这是正常的，跟手机加载模型一样，不是卡住了。**
  工具条切换时会显示“正在切换模型，请稍等…”，请等它，不要连点。
- 切换时上一通生成会被先取消，同一时间只生成一通；切换失败会明确提示原因
  并回落到原模型，不会静默填错模型的回复。
- **同时跑两个服务会占很多内存，日常不要两个黑窗口一起开。** 用管理器时，
  它同一时间只跑一个模型，切换就是停旧起新，不会两个一起占内存。
- 管理器接口（只绑 127.0.0.1:8090，不暴露到网络）：
  `GET /status`、`POST /switch {"modelId": "2507" 或 "35-4b" 或 "8b"}`。

- `start-qwen.bat` / `start-qwen.sh`：只起新模型（18080）。
- `start-qwen-35-4b.bat` / `start-qwen-35-4b.sh`：只起旧 4B（18081）。

  日常不要用这两个单脚本轮换，太麻烦，管理器才是日常路径。

## 回复模式（v1.2.0：四档，跟安卓最终版对齐）

  「重新生成」之前没有检查切换状态，点它们会在管理器杀旧模型时又向旧端口发一通
  生成，先闪一个服务不存在的报错，再被切成功后的重新生成覆盖。现在切模型期间
  全部按钮都 visibly disabled（透明度 0.5、禁止光标），风格/重新生成点击直接忽略，
  切成功后才用新模型 + 当前风格重新生成一次；切失败会回落高亮、恢复按钮可点。
  模型按钮之前只有 return 守卫、没有视觉禁用，现在也有了。
- 其余防打架机制经复核仍成立：单飞行 generationSeq（晚到的旧结果不写回）、
  后台 AbortController（新生成先取消旧请求）、管理器 threading LOCK（同一时间只
  起停一个模型）、同帖同风格同模型正在生成时去重忽略、换帖/关回复框取消上一通、
  模型行与风格行选中态分开作用域（互不抢高亮）。

  无轮询，只有点击 + MutationObserver。
- `styles.css` — 工具栏样式（`qrh-` 前缀，不改 X 布局）。
- `qwen-manager.py` + `start-manager.bat` / `start-manager.sh` — 日常管理器。

## 关键防错

- 只读 `article[data-testid="tweet"]` 里的 `div[data-testid="tweetText"]`，
  不读评论区、不读整页。
- 按帖子 `/status/<id>` 去重：同一帖子 + 同风格 + 同模型正在生成时，重复点击忽略。
- 点另一条帖子、切模型或关闭回复框时，取消上一通生成（v1.2.7 起关闭回复框
  只取消生成并回待命，工具条本身不消失）。
- 找不到回复框时 5 秒超时并明确提示，不会静默卡住。

  测试通过，真实 X 和真实模型仍需用户按 TEST-REPORT.md 的步骤验证一次。
